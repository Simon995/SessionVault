## 待优化项（按代价从小到大）

1. ~~**`svault gc` + `VACUUM`**（≈0.2 GB，零代码）~~ **10-29 订正：省不出东西，而且旧版会删数据。**
   `gc` 的候选是「来由 `reparse`、不是当前头」，少了「与当前头同一个源版本」：回退之后，旧源版本里
   由重解析产生的那一代被当成可再生的删掉，而那批字节已经不在了。10-29 真库的候选 279 份、237,541 条
   全是这一类（10-08 那 78 份之外，又有 201 份是 Codex 10-29 改写留下的）。已修（只读核过：修后候选为 0），
   但**已发布的 v2026.10.10.2 仍带旧条件 —— 换新版之前别拿它跑 `gc --apply`**。
   ⚠️ `gc` 只把页放回空闲表，**文件不缩**，要 `VACUUM` 才还给磁盘；而 `VACUUM` 要独占库。
2. **`history.jsonl` 改增量**（代码改动）：止住增长最快的一块。它只增不改，形状像
   `AppendLog`，当初用 `SnapshotFile` 是权宜（见 AGENTS.md 规则 5 判例）。
3. **`unknown` 旧代的审计清理**（设计先行）：先实测哪些是「当前代已覆盖」、哪些是
   「源已删的唯一副本」，再给人一份可审计的清单。
4. **入库前压缩再加密**（省得最多，估计 >1 GB）。🔴 这是**存储格式变更**：旧版 svault
   解不开新行 ⇒ 先让所有读者支持新格式、再让写者写（AGENTS.md 判据二：两份 svault
   同时开着同一个库，子模块指针拦不住）。
5. **回退留下的旧代：被当前代完整覆盖的才回收**（2026-10-29 记；人定分三步，每步有门）。
   Codex 改写会话的内容时（10-29 WSL 里一批冷会话的 `.jsonl.zst` 被整体重写过一遍），扫描按设计认成
   回退、开新的源版本，旧代永不自动回收 —— 它可能是已消失内容的唯一副本。但改写多半没丢内容，旧代
   多半能在当前代逐条找到。判据只能逐条：整代里**每一条**都能在当前代找到，这一代才可回收；部分覆盖的
   整代保留，不做半删。
   - **第 1 步：量（✅ 10-29）。** `TotalStore::rollback_coverage()` 只读，按两种判据各数一遍。真库结果
     （107 s）：旧代 880 份、617,601 条、1,328.5 MiB。
     - 按**同一条源记录**（`(event_type, EventKey)`）：一条都对不上。带键的 237,541 条全对不上 ——
       Codex 改写时每一行都变了，其余是 v1 遗留、没有键。⇒ 这条判据对 Codex 改写没用。
     - 按**内容相同**（去掉 seq、`EventKey`、归属三项、`schema_version`，多重集）：459,115 条对得上；
       **完整覆盖 521 份、667.8 MiB**。其中 Codex 10-29 改写的那批（WSL）两代旧代 400 份里 396 份完整覆盖、
       513.9 MiB；没完整覆盖的 4 份是 2 个来源各两代，分别有 3 条、35 条在当前代里找不到（Codex 改写时
       去掉或改了），这几代必须留着。
     - 部分覆盖的 359 份（约 660 MiB）主要是 Claude Code 与本机 Codex 的 `unknown` / 早期代：解析器
       升级后字段不同也会算「内容不同」，分不清是真丢还是解析变了，归第 3 项审计。
   - **第 2 步：手动回收（待人定）。** 接在 `svault gc` 上，新加一类候选「被当前代按内容完整覆盖的
     旧源版本」，判据就是第 1 步的「内容相同」。默认预览、`--apply` 才删；执行前退出 QuotaBar /
     TumeFlow、先备份；删完要 `VACUUM` 才缩文件。
   - **第 3 步：放进写入路径（以后，要人拍板）。** 手动回收在真库跑过、判据没出过错之后，再考虑回退时
     当场判覆盖、覆盖就像重解析那样取代旧代。这改的是「回退代永不回收」这条规则（`Projection::Rollback`
     与 `gc_superseded_projections` 的注释），要连判例一起改。

## 复测

```sql
-- 按事件类型
SELECT event_type, count(*), sum(length(event_json)) FROM raw_events GROUP BY 1;

-- 不属于当前代的行，按来由
SELECT coalesce(p.origin, '<无台账>'), count(*), sum(length(r.event_json))
  FROM raw_events r
  LEFT JOIN current_head h USING (source_type, source_location, source_path)
  LEFT JOIN projections  p USING (source_type, source_location, source_path,
                                  source_revision, projection_revision)
 WHERE h.source_path IS NULL
    OR h.source_revision <> r.source_revision
    OR h.projection_revision <> r.projection_revision
 GROUP BY 1;
```

```sh
svault gc --dry-run   # 只统计不删
```

⚠️ 只读打开（`?mode=ro`），别 `cp` 正在被写的库去量 —— 会漏掉 `-wal`。

> 本仓是**原始证据层** —— 只取存储一侧能借鉴的。

⚠️ 官网写「does not store conversations」，但代码里 `store_document_text` **默认开**：原文进
`documents.original_text`，并按 ≈3000 字符切块进 `chunks.chunk_text`，事实经 `chunk_id`
指回原文块、随它级联删除。⇒ 它也留原文，只是不当对话日志。

| 它的做法 | 对本仓 |
| --- | --- |
| **按块内容哈希做增量**：同一文档再写入，只处理哈希变了的块 | 正对 `history.jsonl` 每变一次存一份全文 —— 改成只存新增部分，或按块去重 |
| **「存不存原文」是开关**（关掉则原文列为空，只留抽取结果） | 本仓不能整体关，但可按来源类型定：辅助类来源未必要存全文 |
| **入库前可选脱敏**：按 token 边界锚定的密钥正则（且 `sk-ant-` 排在 `sk-` 前） | 本仓原样加密存。若做，只能是可选项 —— 证据层改写原文就毁了证据 |
| **按字节而非条数限流**（同样「100 块」产出的量能差两个数量级） | 本仓读取预算按条数算，大会话同样会撞上 |
| 后端 Postgres 对大文本自动压缩 —— ⚠️ 这是对 Postgres 的一般了解，**未在其仓库核实** | 反衬本仓「先加密就压不动」：上面第 4 项（先压缩再加密）最值得做 |
