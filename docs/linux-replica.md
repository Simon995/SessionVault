# 总库在多台机器之间同步：决定、现状与方案

> **状态（2026-10-10 晚）**：多机的读写两头都做完了 —— 每个库带标识、主密钥导出 / 导入 / 换钥、
> 合并读取、跨库删除（含按项目根覆盖同一目录的各种写法）。**还没做的是传输**：同步子命令与各机定时任务
> （⑤），等三台装好 Tailscale、实测公司到家里能否直连之后接。待做的全集见 [backlog.md](backlog.md)。
> 数字与「现在如何」停在当天，动手前按文中方法重新量。

## 设计一句话

每台机器只写自己的总库；别的机器的库经中转整库镜像（`sqlite3_rsync`）过来当只读副本；读时合并；
删除记录跨库传播。冲突靠构造避免：一条会话只产生在一台机器上，不让两台写同一个库。

## 决定（按时间；被取代的标出）

2026-10-09：
1. svault 由本仓发布和更新（Windows / Linux），消费方读发布物的路径，不各自内嵌。
2. 无桌面 Linux 的主密钥用受保护的密钥文件；Windows 照旧用 OS 密钥链。
3. ~~逐事件增量复制、副本另用主密钥~~ —— 被决定 5 取代。
4. 先做不依赖主机的部分。

2026-10-10：
5. **传输用整库镜像**：SQLite 官方的 `sqlite3_rsync` 经 SSH。主密钥因此放到用户的每台设备上，中转上没有。
6. **多台机器都写、汇总到一起**：每台只写自己的库，别人的库是只读副本，读时合并。
7. **三台共用一把主密钥**；家里已有库与钥匙的两台用 `key-import --rekey` 换过来（而不是各用各的）。
8. **个人用：家里常开的 Linux 当中转，三台经 Tailscale 组网互通**，`sqlite3_rsync` 经 SSH 走组网。
   取代「经境外中转服务器」：那条线路上行约 62 KB/s（见实测记录）。人确认公司规定允许。
9. **以后给别的用户：用 iroh 把点对点同步做进 svault**，只替换传输层，「每台一库、读时合并」不变。
   取代「用户网盘里放加密小包」：网盘免费容量不够（见下）。
10. 界面做在产品（TumeChat）里，本仓不带界面，只提供命令。

不用同步盘（Dropbox 一类）同步库文件：有写事务时复制库文件会得到一半旧一半新的坏库，`-wal` 也必须与
库文件一起复制，而同步盘逐个文件上传（sqlite.org「How To Corrupt An SQLite Database File」§1.2，
2026-10-10 查证）；同步原始会话文件也不行 —— 会话工具按期清理旧记录，删除会同步过去，而早期会话往往
只剩总库这一份。网盘免费版也放不下：Dropbox Basic 2 GB、限 3 台设备；坚果云免费版每月上传 1 GB、
下载 3 GB、单文件 ≤ 500 MB（第三方汇总，官网未核，查于 2026-10-10）。

## 方案（现行）

### 布局与一轮同步（⑤，待做）

- 每台机器：本机库 `<data_local_dir>/svault/total_store.db`，副本目录 `<data_local_dir>/svault/replicas/<store_id>.db`。
- 中转（家里 Linux）上每台一个库：`<目录>/<store_id>.db`。一轮：推本机库 → **到中转核对副本**
  （`store_id` 对、最大 offset 不小于推之前本机的）→ 列出别的机器的库 → 逐个拉 → **在本机核对** →
  `adopt-erasures`。每一步失败重试；加锁防两轮重叠。
- 必须处理的事实：
  - `sqlite3_rsync` 远端起不来时**仍返回 0**、也不建副本（对照实测）；推送中途断线会在中转上留下
    0 字节的库加 `-journal`。所以每轮之后自己核对，不信退出码。
  - Windows 自带的 `ssh.exe`（OpenSSH_for_Windows 9.5p1）配 `sqlite3_rsync` 会**卡死**（两端都起来了，
    第一条协议消息都过不去）；Git 自带的 ssh（10.3p1）能传 —— Windows 上 `--ssh` 指它。
  - 官方 Linux 预编译版 `sqlite3_rsync` 要 glibc 2.38（Ubuntu 22.04 跑不了、24.04 可以）；按官方 `main.mk`
    的 `RSYNC_OPT` 从源码编出的只要 2.34 —— 打算由 `release.py` 一并编、一并发布。
  - 每轮都对两端整库算校验，耗时随库大小线性增长（5 GB 约 16 s）。

### 密钥（②）

每个用户一把主密钥，他的所有设备共用；新设备 `key-import` 一次。已有库的设备 `key-import --rekey`：
先确认库没被别的进程开着（只有 Windows 查得出）→ 旧钥匙备份到旁边 → 一个事务里改包全部数据密钥并记下
备份位置 → 最后换本机钥匙；正文不动；可重跑，也修「换钥时写入方没退出」留下的旧钥匙数据密钥。
**换钥前先退出 QuotaBar / TumeFlow**。中转上没有主密钥，看不到 `event_json`，但看得到明文列：
`raw_events` 的 `source_path` / `project_root` / 会话 ID / 时间，`project_identity` 的 `canonical_id`，
注册表里的根路径。

### 合并读取（③）

- `stores` 列出本机库与副本目录里的每个库；打不开的列成 `store_unavailable`，副本目录列不出来报错退出。
- `pull` / `changes` 仍一次读一个库（`--store`），摘要带 `store_id`，消费方的游标按它分开记。
- `sessions-read` / `sessions-recent --all-stores`：同一会话在几个库里都有时，取当前投影事件最多的那份，
  一样多取 `store_id` 小的 —— 只看内容与库标识，在哪台机器上读都挑出同一份（TumeChat 按规则 2 提的判据）。
  输出写明 `found_in`、`erased`、`stores_searched` / `stores_unavailable`：「这台机器找不到」「删了」
  「原文变了」是三件不同的事。没有 `store_id` 的库不参与合读。
- 同一个项目按 `canonical_id` 归并，没有远端的按机器分开。

### 删除（④）

- `erase` 的删除记录写在执行者自己的库里；合读遵守所有库的删除记录；`adopt-erasures`（同步每轮跑）
  把别的机器的删除记录收进本机库并删掉本机原文。`erasures [--all-stores]` 给消费方删自己的索引。
- 按项目根删：库里与它**同一目录的各种写法**（`attribution::registry_key` 判同一：UNC 写法与规范形、
  发行版里的 `/mnt/<盘>`；`erase` / `adopt-erasures` 带本机挂载表时盘符与 `/mnt` 也互认）各记一条墓碑、
  一起删。合读判项目根被删按比较键、不带挂载表（不为此起 `wsl.exe`）—— 盘符与 `/mnt` 那一对要等
  会话所属的机器收下删除记录才消失。
- 路径类删除记录按比较键在每台机器上照删：两台机器若有同一路径，会一起删。按会话删没有这个问题。

### 已做的基础（一、二、三）

- **只读打开不迁移**：`TotalStore::open_read_only[_with_key]`、`open_existing`；「应有的表结构」取自本程序
  自己的 `migrate()`；库缺表列报 `SchemaBehind`。守护：`store.rs` 单元测试 + `tests/cli_read_only_it.rs`。
- **主密钥文件**：`SVAULT_KEY_FILE`，建出来就是 `0600`，对组或其他用户开放了权限就拒绝，丢了不重新生成。
  部署建议：用 systemd 的加密凭据把密钥文件交给服务，不明文落盘。
- **发布**：`scripts/release.py <tag>`（`--publish` 才打标签、发 GitHub Release、装到 `%LOCALAPPDATA%\svault\bin`）；
  编译时把家目录映射成 `~`，编完逐字节扫描，二进制里嵌着本机家目录就拒绝发布。家里 Linux 上的安装位置待定。

## 实测记录（2026-10-10）

- **`sqlite3_rsync` 3.54.0 对本库**：真库副本（5.03 GiB、163 万行事件）Windows 本机首次 18.7 s；无变化一轮
  约 16 s、传约 30 KB；`erase` 一个会话后一轮传 1.2 MB，墓碑同到；源库每 50 ms 提交一次时同步，副本是同步
  开始那一刻的一致快照；以在用的真库为源直接同步，副本完好、svault 读得动。Windows ↔ Linux 经字节管道
  （假 ssh）推、拉、增量均逐表一致。
- **经境外中转服务器（Ubuntu 24.04，地址与账号只在各机本地配置里）**：专用普通账号（不能 sudo、密码锁定），
  `relay/`（700），每台机器用自己的钥匙、`authorized_keys` 带 `restrict`；`sqlite3_rsync` 与 `sqlite3` 3.54.0
  装在 `/usr/local/bin`，哈希核对一致。Windows 自带 `ssh-keyscan` 不支持服务器的 `sntrup761x25519` 密钥交换，
  用 Git 自带的取、指纹核对一致才写进 `known_hosts`。线路：直连 SSH 上行约 10 KB/s、偶发超时与
  `Connection reset`；经本机代理上行约 62 KB/s、下行约 2.2 MB/s —— 瓶颈是**出境**那一段。这台现在只留作测试。

## 以后给别的用户（决定 9：iroh）

- **传输**：iroh（Rust 点对点库，1.0 于 2026-06 发布）：按公钥拨号、先打洞直连、失败才走中继，中继可自建；
  iroh-blobs 做可续传、带校验的大文件传输。来源：lib.rs/crates/iroh、docs.iroh.computer（查于 2026-10-10）。
  数据只在用户自己的设备上，开发者手上没有用户数据，也没有网盘容量问题。
- **新设备拿钥匙**，三种都给：**同步密码**（主密钥用它经 Argon2id 派生的钥匙加密；能被离线猜，所以要够强；
  忘了只能靠恢复码）；**设备配对**（两端屏幕核对短码后，老设备把主密钥用新设备的公钥加密交给它）；
  **恢复码**兜底。设备列表可查可移除；移除收不回已经拿到的旧数据，要断干净得换钥。
- **登录**（微信扫码 / 谷歌账号）只解决「你是谁」，不分发密钥。微信网站登录要审核通过的网站应用、
  `AppSecret` 只能在服务端换 token（官方文档，2026-10-10 查证），即要自建账号服务器；个人主体能否认证
  官方页没写，第三方多称只支持企业（未核）。自建「邮箱 + 密码」账号要自己的服务器与合规成本，只有
  付费 / 团队这类功能才值得；即便做，「重置密码」只找回账号，找不回数据。

## 历史前提（2026-10-09 实测；已解决的写明怎么解决）

| 当时的事实 | 现在 |
| --- | --- |
| 主密钥在 OS 密钥链，数据密钥包裹后存库内 `data_keys`：只拷库文件读不出 | 仍是；多机靠共用一把主密钥（决定 7） |
| 库里已有加密行而没有主密钥时报 `MissingKey`，不会新建一把错钥 | 仍是 |
| 无桌面 Linux 上 `keyring` 走 Secret Service，连空库都建不出 | 已解决：`SVAULT_KEY_FILE` |
| 每次打开总库都跑 `migrate()`，包括 `open_existing` | 已解决：只读打开不迁移；`open_existing` 也已改为只读 |
| `erase` 没有对外出口，删除同步不到副本 | 已解决：`erasures` / `adopt-erasures`，合读遵守所有库的删除记录 |
| 本仓没有任何发布物 | 已解决：GitHub Release + 本机安装 |

外部输入（会过期）：Claude Code 默认清理 30 天以前的会话记录（`cleanupPeriodDays`），早期会话在本机常常
只剩总库这一份 —— 副本也因此兼作备份。
